Go 1.21 / PostgreSQL lab-management portal. ~13k lines of Go, split into a thin main binary and eight domain packages under internal/. This document captures the high-level architecture, the request-lifecycle data flow, and per-module function-level flowcharts with descriptions.

1. Executive summary

SampleDB follows a classic layered monolith pattern: a single Go HTTP server receives requests, runs them through auth middleware, dispatches to per-domain handlers, which call per-domain service objects that talk to PostgreSQL through a pgx connection pool. The internal/app package owns wiring; main.go only handles config, template pre-parse, and server start.

The app exposes two parallel interfaces over the same services: an HTML UI (server-rendered templates, with HTMX partials) and a JSON REST API under /api/v1 sharing identical auth, identical services, identical validation.

ConcernChoice
HTTP multiplexerstdlib net/http.ServeMux (no 3rd-party router)
Database drivergithub.com/jackc/pgx/v5 with pool interface (dbiface.Pool) for testability
AuthSession cookie + Bearer token (SHA-256 hashed, one-time display)

2. High-level architecture

The system is organised into four vertical layers (entry → middleware → domain → storage) and six domain modules. Every domain exposes a Service interface (business rules + SQL) and a Handlers struct (HTTP glue, template data, HTMX partials, REST JSON). Both layers are constructed in app.RegisterRoutes and attached to one shared ServeMux.

3. Request lifecycle (dataflow)

Every authenticated request — HTML or JSON — follows the same pipeline. The only branches are at auth resolution (cookie vs Bearer) and at render (template vs JSON). HTMX requests reuse the same handlers and receive section partials (via Renderer.RenderSection) instead of full pages.

  end

(web.ExtractID*, DecodeJSON)
  Hd->>Sv: service call (e.g. Create, Update, ListAll)
  Sv->>P: pgx query (QueryRow / Query / Exec / Begin)
  P-->>Sv: rows / tag / error
  Sv-->>Hd: domain struct or ErrNotFound / ErrForbidden / ErrConflict

  opt File upload / download
    Hd->>F: save / read uploaded file
(sanitizeFilename, generateUniqueFilename)
  end

  alt HTML request
    alt Full page
      Hd->>R: Render("page", data)
    else HTMX partial (HX-Request: true)

    end
    R-->>C: text/html
  else JSON request (/api/v1/*)
    Hd->>Hd: web.JSON(status, v) or writeError
    Hd-->>C: application/json
  end

Auth resolution detail

auth.Manager.RequireAuth is the single gate. It calls TryAuth(r), which inspects the request in this order and returns a Session on first hit:

  1. Authorization: Bearer <token> — SHA-256 hash the token, look it up in api_tokens, fetch owner user_id, update last_used_at.
  2. session cookie — SHA-256 hash, look up in sessions with expires_at > now(), hydrate {UserID, Username}.
  3. Neither → content-negotiated fallback: HTML paths get 302 /login, paths under /api/ get 401 {"error":"unauthorized"}.

4.7 internal/dbschema

Single exported function — Ensure(ctx, pool) — run at boot. It executes a fixed list of CREATE TABLE IF NOT EXISTS, CREATE INDEX IF NOT EXISTS, and additive ALTER TABLE … ADD COLUMN IF NOT EXISTS statements so the schema converges to the target DDL (which is also kept as a human-readable copy in DDL/init.sql).

Migration model: idempotent forward-only DDL, no versioning table. Safe because every statement is IF NOT EXISTS / ADD COLUMN IF NOT EXISTS. Downside: no rollback and no ordering guarantees across multiple app instances booting simultaneously.

Notable observations from the walk-through
  • Three root-level Go files are stubs (fabrication_steps.go, sharing.go, owner_test.go, fabrication_steps_test.go, fabrication_steps_handler.go are all 13 bytes — effectively empty package declarations). The real implementations live in internal/samples.
  • Booking conflict detection uses Postgres' EXCLUDE USING gist on a tstzrange (inferred from the error-code handling); the Go-side CheckConflict is a best-effort pre-check, the DB is the source of truth.
  • The app.RequireAdmin middleware re-queries users.admin on every admin request rather than trusting a cached flag on the session — a good defense against stale sessions after a demotion.
  • Admin mutations that change a user's effective permissions call Auth.RevokeUserSessions so cookies are invalidated immediately (belt-and-braces alongside the deleted / is_approved flags that RequireAuth checks).
